# big-text: how it is built

big-text shows a corpus as one surface: a hierarchy of rectangles, each leaf a block of lines, drawn at a level of detail chosen from its size on screen. Three stages: an index (one script per corpus), a layout, a viewer. The viewer never learns which corpus it is showing; this document says what it gets, stage by stage, and what it does with it. The README says why.

Platform: Python 3.12, numpy, Pillow, PyOpenGL, glfw, OpenGL 3.3 core, the same stack and conventions as big-picture. Shaders are GLSL 330 core and use nothing without a GLES 3.0 equivalent (no geometry shaders, no bindless, no double), so a WebGL2 viewer could link them. Everything of the corpus is resident on the GPU; a streaming working set is a later step (README, open question 4). All scripts are `#!/usr/bin/env python3`, argparse, a positional main argument, `--out` optional with a derived default; plain functions and numpy for bulk data.

## Stage 1: the index

An index is `data/<name>_atlas/index.npz` plus `index.json`. Any script that writes one is a corpus adapter; two exist.

`atlas_index.py <src_dir>...` indexes a source tree. It walks the tree (`git ls-files` inside a repository so `.gitignore` holds, a plain walk otherwise), skipping `.git`, `target`, `node_modules`, `__pycache__`, `.venv`, `data`, submodules unless `--submodules`, files over 4 MB, and anything that is not text (a NUL in the first 8 KB, or UTF-8 with more than 1 percent of replacement characters). Several source directories are indexed as subtrees of their common parent. Every kept file becomes lines: tabs to 4 spaces, every character outside printable ASCII to `?` so one byte is one column, trailing whitespace stripped, 4096 columns at most. Files are sorted by path within their directory and directories depth-first, so a directory's files and all its descendants' files are one contiguous range of file indices and of line indices; the viewer draws visible files as runs of that order.

A small regex tokenizer per language family (Rust, C-like, Python, shell, and text variants that only know which comment syntax applies) gives every character one kind:

| kind | value | what |
|---|---|---|
| space | 0 | whitespace |
| ident | 1 | identifiers |
| keyword | 2 | language keywords |
| type | 3 | identifiers starting with an uppercase letter |
| string | 4 | string and char literals, including quotes |
| comment | 5 | comments, including markers |
| number | 6 | numeric literals |
| punct | 7 | operators, brackets, punctuation |
| macro | 8 | Rust `name!`, `#[attributes]`, C preprocessor lines, Python decorators |
| call | 9 | an identifier followed by `(`, and the name in a definition |

Block comments and multi-line strings carry across lines within a file. The aim is the pastel texture at three pixels per line, not parser accuracy. Items (for outlines and the hover label) come from regexes on line starts with the extent found by brace or indentation matching: Rust `fn struct enum trait impl mod macro_rules type const static`, Python `def class`, C-like `struct enum union class` and a function heuristic. Item kinds: 1 function, 2 struct, 3 enum, 4 impl or trait, 5 other. Nested items are kept. The tokenizer runs in a process pool (`--workers`, default half the cores): emscripten's 2.8 million lines in about 2 seconds, before the git pass.

Inside a git checkout the same run gives every file its tint: one `git log --numstat --no-renames` over the indexed directories (a rename is a removal and an addition), each file's lines added and removed summed over the whole history, on a log scale to 0..1, labelled `churn`. `--no-git` skips it; a tree that is not a checkout gets no tint.

`book_index.py` writes the same index from a Project Gutenberg text; see the book section at the end.

`index.npz`:

| array | dtype | shape | meaning |
|---|---|---|---|
| chars | uint8 | [total] | every line's characters, files and lines concatenated with no separators |
| kinds | uint8 | [total] | kind per character |
| line_off | uint64 | [n_lines + 1] | start of each line in chars |
| line_file | uint32 | [n_lines] | file of each line |
| line_indent | uint16 | [n_lines] | columns of leading whitespace |
| line_len | uint16 | [n_lines] | columns |
| file_line0 | uint32 | [n_files + 1] | first line of each file |
| file_chars | uint32 | [n_files] | non-space characters |
| file_dir | uint32 | [n_files] | directory index |
| item_file, item_start, item_end | uint32 | [n_items] | file, first line and one past the last line, file-relative |
| item_kind | uint8 | [n_items] | |
| file_tint | float32 | [n_files] | optional: the tint in 0..1 |

`index.json` holds `root`, `name`, `files` (path, lang, lines, bytes), `dirs` (path, parent, children, files, top: the top-level ancestor that selects the hue), `items` (file, start, end, kind, name), `kinds`, `stats`, and optionally `tint` (the tint's one-word label), `scheme` (the corpus's look: `ground`, `page`, `bar`, `band` for one colour on every directory band instead of the hues, `kinds` as ten hex colours, `items` as five, `ink` as the bars' alpha far and near and the blocks', `font`, a face under `fonts/`, `leading` over its ink extents, and `justify`; every key optional, the code atlas's dark scheme the default and its ink measured at load) and an adapter's own keys (a book's `corpus` and `page_lines`).

## Stage 2: the layout

`atlas_layout.py data/<name>_atlas [--aspect 16:9] [--preview out.png]` writes `layout.npz` plus `layout.json`. The world is [0, 1600] by [0, 1600 / aspect], y down, float64 on the CPU and float32 on the GPU (float32 error at 1600 is 1e-4 units, under 0.1 percent of the smallest pitch of a 3 million line corpus).

A squarified treemap (Bruls, Huizing, van Wijk) over the directory tree, every file's area its weight: tokens for code (runs of one non-space kind, restarted at every line), lines for a book. Inside a directory rectangle, first inset by the padding, then squarify the files and subdirectories together, biggest first. The padding is two line pitches of the directory's typical file, the pitch estimated as the square root of the directory's area over its lines times the area a line takes at unit pitch (about 34: one pitch tall, sixty characters of 0.571 pitch wide), clamped to [0.01, 4] world units and a quarter of the shorter side; the viewer draws it as the directory band, capped at 3 points, so the band is a hairline at the fit and never more than a few pixels, and the padding beyond it a gutter of about two lines once the directory's text is legible.

A file's rectangle is split into k equal columns with a gap of 6 percent of the column width. Each column holds `rows = ceil(n_rows / k)` rows at pitch `p = h / (rows + 2)` (one pitch of margin above and below); the column's capacity in characters is `cap = floor(col_w / (p * A))` with A the font's character advance over its line pitch (0.571 for the bundled face, from atlas_font.py). k is the most columns whose capacity still reaches `target = clamp(p90 of the file's line lengths, 24, 100)`, at most 64. Lines longer than the capacity wrap inside the column: continuation rows hang in by two characters and hold `cap - 2` characters each; columns narrower than 16 characters clip instead. The row count depends on the capacity and the capacity on the pitch, so the two are iterated to a fixed point. Every item spans one rectangle per column it crosses. A book skips the treemap and the column search; see the book section. When the scheme names a proportional face, widths replace character counts throughout: every line's width in line heights is the sum of its glyphs' advances, columns are chosen and lines wrapped by width (a line breaks where the next glyph would end past the column, continuation rows hanging in by two mean advances), the pitch is iterated until every file's exact rows fit its columns, and the layout writes `char_x`, each glyph's x within its row in line heights, and `row_width`; a monospace corpus gets `row_width` alone. With the scheme's `justify`, a row whose line has more of its paragraph after it (the next line of the file is not blank, the line starts at the margin, a wrapped line's earlier rows always, and a page's footer when the index says its last line is one) is stretched to the column's capacity by widening its word gaps evenly, in `char_x`, unless the stretch would exceed 35 percent; the scheme's `leading` stretches the line box over the ink extents, half above and half below, for every use of the face.

`layout.npz`:

| array | dtype | shape | meaning |
|---|---|---|---|
| world | float64 | [2] | W, H |
| dir_rect | float64 | [n_dirs, 4] | the outer rectangle, before padding |
| dir_pad | float64 | [n_dirs] | padding width |
| dir_depth | uint16 | [n_dirs] | root is 0 |
| dir_hue | uint8 | [n_dirs] | top-level child index mod 12 |
| file_rect | float64 | [n_files, 4] | |
| file_text | float64 | [n_files, 4] | the text block: the file inset by a book page's margins, the file itself for code |
| file_pitch | float64 | [n_files] | line pitch in world units |
| file_cols, file_rows, file_cap | uint16, uint32, uint16 | [n_files] | columns, rows per column, characters per column |
| file_colw | float64 | [n_files] | column width including its gap |
| file_hue | uint8 | [n_files] | the top-level directory's hue |
| file_row0 | uint32 | [n_files + 1] | first visual row of each file |
| file_weight | float64 | [n_files] | the weight, for the heights in 3D |
| file_dir | uint32 | [n_files] | |
| line_row0 | uint32 | [n_lines + 1] | first visual row of each line |
| row_line, row_col0, row_len | uint32, uint16, uint16 | [n_rows] | the line a row shows, its first column, its length |
| row_pos | float32 | [n_rows, 2] | top left of the row's cell |
| row_width | float32 | [n_rows] | the row's width in line heights |

| item_rect | float32 | [n_item_rects, 4] | |
| item_rect_item | uint32 | [n_item_rects] | index into items |

`layout.json`: `world`, `aspect`, `weight` (`tokens` or `lines`), `flat` (true for a book: nothing rises in 3D), `char_aspect`, `proportional`, `font`, `hang` (2), and `dirs` with each directory's label (its own name with a trailing slash; the root's is the corpus name), rect, depth, hue, parent, children and files.

`--preview` renders the layout with Pillow at 2400 pixels wide, the layout's own test. `tests/check_layout.py` checks the invariants against the layout's own tree (a book's flow layout keeps the root alone): dtypes and shapes, every file inside its directory's inner rectangle and every directory inside its parent's, no overlapping siblings, every row cell inside its file, the rows of a line covering exactly its characters, item rectangles inside their file, every item with at least one rectangle.

## Stage 3: the viewer

`atlas_viewer.py data/<name>_atlas` opens a glfw window with an OpenGL 3.3 core context, sized to the screen's work area so the framebuffer is the same in every run (2940 by 1640 on the development machine); every pixel threshold below is in device pixels. The map's viewport is the window minus a top strip holding the input hints (the keys this corpus answers to, dimmed) and the filter box, a bottom strip holding the crumb trail and the status line, and the right column while the results panel is open; the map is drawn, fitted, hit-tested and scripted in that viewport, and a fitted map refits when the panel opens or closes.

### Camera

(cx, cy, zoom) in float64, zoom being device pixels per world unit; the shaders get one model-view-projection matrix. The wheel zooms about the cursor with a glide: each tick adds to a zoom velocity that decays with a 0.12 s time constant. Left or right drag pans with the map following the cursor exactly. The zoom is limited to half the fit and to 400 pixels per line for the file under the cursor (or the view centre), falling back to the line-weighted median pitch; a clamp never moves the zoom against the gesture. `R` resets the view to the fitted map. Fly-to is van Wijk and Nuij's smooth zoom-and-pan with rho 1.4, 0.3 to 1.2 seconds, so a hop between distant places zooms out and back in. A double click (two presses within 0.35 s and 4 points) flies to the extents of the file under the cursor, or of the deepest directory there, and remembers the view it left; a second double click on the same rectangle while the camera is still at those extents flies back.

In 3D (`3`, `--proj 3d`, or Alt-drag, which tilts vertically and turns horizontally from 0 to 70 degrees) the camera orbits a focus point at the tilt and yaw, at the distance where one world unit at the focus is still `zoom` pixels, so the zoom semantics and the per-file LOD hold and one frame has text near and bars far. By default nothing rises: the tilt is only a way of looking at the sheet. With the heights on (`H`, `--heights`) directories are terraces of 5 world units per level, files rise from their terrace by 90 units times the square root of their weight over the largest, an instanced wall pass draws the sides shaded by facing, and the focus height follows the roof of the file under the centre so a close camera never ends up inside a building; the toggle recomputes and re-uploads the file and directory texels only. A flat layout keeps the heights off.

### GPU data

Uploaded once at start: `tex_chars` and `tex_kinds` (R8UI, width 16384, a byte offset maps to (o mod 16384, o div 16384); more than 16384 squared characters refuses to start), `tex_line_f` (RGBA32F, width 4096, one texel per visual row: x, y, row index within the file) and `tex_line_u` (RGBA32UI: byte offset low, file, indent | len << 16, byte offset high), `tex_file_f` (three texels per file: the rectangle; pitch, column width, capacity, hue; z base, height, tint), `tex_file_u` (RGBA8UI, one texel per file, updated every frame: LOD, flags, sampling step as two bytes; flags bit 0 hovered, bit 1 has hits, bit 2 the current hit's file, bit 3 dimmed), `tex_dir_f` (three texels per directory: rectangle; padding, depth, hue; z base, height), the raster glyph atlas with mipmaps, the UI's own atlas from the bundled monospace face, the vector tier's curve and band textures, and for a proportional face `tex_char_f` (RG32F, width 16384, one texel per character: its row and its x within the row). Item rectangles, hit rectangles and UI boxes and text are instanced from small per-frame buffers. Everything is a unit quad instanced with `gl_InstanceID` and `texelFetch`; no texture buffers, no SSBOs.

### The levels of detail

Per frame, in numpy over files: pixels per line `ppl = file_pitch * zoom`, foreshortened in 3D by the file's depth; the LOD; visibility; for LOD 0 the sampling step `ceil(1 / ppl)`. One `line.glsl` draw per run of consecutive visible files, its vertex shader making a degenerate quad for rows outside the view or skipped by the step.

| LOD | ppl | drawn |
|---|---|---|
| 0 sampled bars | under 1 | every step-th row as a grey bar exactly one pixel tall at its own depth, from indent to length, so the density stays about one bar per pixel row; the kind bands beneath |
| 1 line bars | 1 to 3 | one grey bar per row from indent to length; the kind bands beneath |
| 2 tokens | 3 to 6 | one block per character in its kind colour; item outlines |
| 3 text | 6 and up | glyphs in the kind colour, from the raster atlas below 12 px per line and from the vector tier above; item outlines |

A proportional face draws the tokens and text LODs with `glyph.glsl` instead, one instanced quad per character of each run of visible files, placed at its row's position plus its x and sized by its advance from a 96-entry uniform, the same LODs' fragment code applied per glyph, the raster cell sampled over the glyph's own advance; `line.glsl` then keeps LODs 0 and 1. The kind bands are the item rectangles of LOD 0 and 1 files filled in the item kind colour at 18 percent (fills far, outlines near); at LODs 2 and 3 the same rectangles are 1.5 pixel outlines. Every LOD draws the file background `#111114` under the lines, so nothing flips colour at a cut; the hue lives only in the directory bands. The border is one grey pixel, two yellow for a hit file, three for the current hit's file, computed in the fragment shader from the world distance to the edge and `fwidth` so it holds in perspective, and drawn twice: with the fill before the lines and as a ring after them, so column-0 text never breaks a hit outline. The hovered file gets the light border and no fill, so its text stays readable. The tint, when on (`C`, `--tint`), mixes the fill towards ember by the file's value; bars and glyphs are untouched, and the status line shows the label. The bars' alpha eases with pixels per line from the scheme's far ink at one to its near ink at three, and the blocks take its block ink. A scheme that names no ink, code's, is measured by the viewer at load with `atlas_font.mean_ink` over the corpus's characters: the blocks at the text's ink over the 0.7 of a row they stand tall (0.245 for JetBrains Mono over emscripten), the near bars a quarter above that, the far bars at 0.55 for the die shot. The book's are measured at index time by the same function, the mean coverage of a glyph's advance box in the face's atlas averaged over the book's letter frequencies (15.6 percent for Literata), divided by the 0.7 of a row that bars and blocks stand tall, the bars' scaled by the share of characters that are not spaces since bars span them, so each level has the mean ink of the text it replaces and nothing steps at a cut, whatever the face. The ground, page, bar, kind and item colours are the scheme's, uniforms set once at start; the UI boxes, the hues and the yellow of the hits are the viewer's own. Dimmed files (no hits while a filter is active) darken their fill by half and their bars and glyphs to 45 percent.

### Glyphs

`atlas_font.py` rasterises the 224 glyphs of Windows-1252, bytes 32 to 255, of a face into a 16 by 14 grid at a 64 pixel cell, mipmapped and sampled trilinearly, the line box still the ASCII ink extents so accents ride in the leading; a proportional face's cells are as wide as its widest glyph, each glyph drawn from the left, and the metrics carry every glyph's advance in line heights. The UI text always comes from the bundled monospace face's atlas. The line box is the face's ASCII ink extents rather than its OS/2 box, so a change of face does not change the layout's proportions (JetBrains Mono's OS/2 box carries 1.32 em of leading; the ink box is 1.05 em). `vt_glyphs.py` builds the vector tier for the same 224 glyphs in Slug's form: quadratic outlines from fontTools (cubics subdivided within 0.5 units on a 1000 unit em) as float32 control points in a curve texture, and per glyph horizontal and vertical bands over its ink box, each listing the curves that cross it sorted for the shader's early exit, widened by half a pixel at 12 px per line. `shaders/vt_glyph.glsl` is a GLSL translation of the reference pixel shader: the sign-bit root rule, two axis rays with a box filter, the weighted combination. The data is built on first run and cached under `data/`; `tests/test_vt_glyphs.py` compares the tier against Pillow, `tests/bench_vt.py` measures both tiers against an eight times supersampled reference and produced the README's table, which put the handoff at 12 px per line.

### Hover, crumbs, filter

A coarse 64-wide grid over the world makes the file under a point O(1); the row and column inside it come from the file's layout, following the wrap, the column by dividing x by the advance for a monospace face and by a search over the row's glyph x's for a proportional one; hit rectangles and fly-to targets use the same offsets. The hover label is the path, then `:line` and the enclosing item's keyword and name at LODs 2 and 3, then the file's hit count at the text LOD. The crumb trail names where the view centre is: the corpus, then the path of the file under the centre, or of the deepest directory there. Directory tags are drawn for visible directories at least 48 pixels across, never scaled, skipped when wider than 40 percent of the rectangle, at the top-left of the visible part of the directory's inner rectangle, so a directory zoomed into keeps its tag at the corner of the view; a tag that would sit on an ancestor's slides right along the top edge past it, so nesting reads as a trail, and a directory filled by exactly one child draws no tag, the innermost of such a chain joining the names (`system · lib · libc`).

The filter (`/` or a click in the box; `Backspace`; `Escape` clears) runs from two characters: a case-sensitive whole-word regex over a newline-joined copy of the corpus (one byte per line extra, so word boundaries hold at line ends), in a thread, in 1 MB chunks with pos and endpos so the boundary context is kept, yielding between chunks; a mention inside a comment or a string is not a hit. The panel, 180 points wide in its own column, lists the hits by file with the line number and the line's text windowed around the hit; the status line counts hits and files; `Enter`, `Down` or `]` and `Up` or `[` step through them with a fly-to that ends at about 40 lines by 100 columns, and a click on a row does the same. Hit files get the yellow border at every zoom and the rest dim.

### Scripting

`--frames N` runs N frames of the opening zoom (fit to 16 px per line at the corpus centre) and exits; `--screenshot` saves the last frame; `--goto path[:line]`, `--zoom`, `--filter`, `--step`, `--hover path:line:col`, `--proj 3d --tilt --yaw`, `--heights` and `--tint` pin the view first; `--no-hover` keeps the cursor off the centre file; `--stats` prints load time, GPU memory and the mean and 99th percentile frame time; `--shots DIR` writes the standard set (docs/shots/README.md). Real input is ignored during a scripted run. `tests/test_viewer_input.py` drives the callbacks on the synthetic corpus of `tests/gen_synthetic_atlas.py`.

## The book adapter: War and Peace

The README's adapter split (a hierarchy, a layout, an aggregate colour per corpus; everything else shared) was tried on Dobbie's own example, the whole of War and Peace, and held: one indexer and one placement function, no new shader, no viewer change but a parser fix.

`book_index.py` reads a Project Gutenberg plain text (`--gutenberg N` fetches `https://www.gutenberg.org/cache/epub/N/pgN.txt` into `data/gutenberg/` once) and writes the same `index.npz` + `index.json` as `atlas_index.py`, through the `write_index` function shared with stage 1. The prose is reflowed first: every paragraph, a run of non-blank lines with a line of 60 characters or more (the contents list, verse and headings keep theirs), is joined and filled word by word to the line width, in the face's advances, that makes a page of `--page-lines` (40) lines plus its two blanks and footer, inside the margins, a page of `--page-aspect` (Letter); `--no-reflow` keeps Gutenberg's breaks. The hierarchy is parts over chapters over pages: a heading at column 0 such as `BOOK ONE: 1805`, `PART I` or `FIRST EPILOGUE: 1813 - 20` opens a part, `CHAPTER I` a chapter, and every `--page-lines` (40) lines of a chapter are one page, numbered through the book (`Book One: 1805/Chapter I/p. 17`); a page never starts with a blank line, runs of blank lines are squeezed to one, a chapter ends its last page early. The contents listing indents its copies of every heading, which is what keeps it out of the structure. The parts are the directories (18 with the front matter) and the pages the files; chapters are in the page paths only, so the layout is a grid of pages per part, as printed, and the hover label carries the chapter. Gutenberg's header and footer, outside the `*** START` and `*** END` lines, are dropped. A text with no heading at all is one part named after the corpus, its pages `name/p. N`, so any plain text file is a book. Text is kept in Windows-1252, composed (NFC), a few characters outside it respelled (the no-break space, the Unicode hyphens and primes), the rest `?`: curly quotes, dashes, the ellipsis and accented letters stay as they are, and `index.json` names the encoding so the viewer searches and prints lines in it. The prose tokenizer counts bytes above 127 as letters, so an accented word is one word. A `prose` tokenizer spec gives words the ident kind and numbers the number kind, with no string literals (a line of dialogue is not a string) and no items. Every page is padded to its 40 lines and given two blank lines and a running footer, author, page number and title spaced across the page width in the face's own advances (the 99.5th percentile of the book's line widths), its characters in the comment kind so the scheme greys them; chapter headings are centred on the same width; the author and title come from Gutenberg's header, its lowercase honorific dropped. The index carries the book's scheme, taken from Dobbie's demo: pages as white quads, text black, on the `#a0a9af` ground his page clears to, the bands in that ground colour so nothing marks a part but the crumb trail, the face (`--font`, any file under the repository) with its leading and its measured ink; the face of his demo came from the source PDF and is not recorded anywhere reachable, and the book's face is Literata, the OFL book serif, proportional, through the width-based layout and the per-glyph draw described under the stages above. War and Peace: 18 parts, 366 chapters, 1,401 pages, 63,191 lines, 3.14 M characters, 2.63 M glyphs, 0.46 s; Dobbie's reflowed pages numbered 1,273.

`atlas_layout.py` reads `"corpus": "book"` and `"page_lines"` from the index and skips the treemap. The default, `book_flow`, is one grid of every page in reading order, as Dobbie's demo: the layout's tree is the root alone, the parts draw nothing, every page sits in a gutter of 8 percent of the cell's width, and its text block is the page inset by margins of 7.5 percent of its width, 9 percent of its height above and 3 below (`file_text` in the layout, the file itself for code; the viewer's hover reads from it), 58 pages across for War and Peace. Every page is `page_rows` rows, the 40 text lines, two blanks and the footer, so the footer sits in the bottom margin. `--book-layout parts` keeps the earlier `book_layout`: every part a full-width band of whole page rows stacked in reading order, every page one cell of one size, rows filled left to right, a part's last row short. The column count is the one that brings a cell closest to the page aspect (the book's 99.5th-percentile line width times the character aspect, over the page's lines plus two) from the wide side, so a page's single column always holds its lines: 65 across for War and Peace, 16 wrapped rows in the whole book (the few lines past 73 columns). `layout_files` takes a `page` argument that pitches every file as a full page aimed at the book's line width, so a short last page keeps its chapter's text size and no page splits into columns. A book's weight is lines, so every page is one cell whatever its length, and its layout declares itself flat: in 3D nothing rises, the tilted view is the sheet in perspective. The code rule, a file's height as the square root of its weight and a terrace per directory level, made the book a city of near-equal blocks under tokens and a plateau with dips at chapter ends under lines, and equal heights still left the Books as terraces; a book is one sheet. The strip treemap (Bederson et al.) was tried first with chapters as directories and rejected: pages came out at every size and shape, which is the code map's look, not a book's. The empty end of each band is the price of parts as rectangles; letting a part start mid-row would make it a non-rectangle, which nothing in the viewer draws.

The viewer needed one fix: `--goto` split its argument at the first colon, and a book's paths hold colons (`Book One: 1805/...`); it now splits at the last colon and only when a line number follows. The frame loop measured 2.4 ms mean over the scripted zoom (9.1 MB on the GPU). Screenshots and their commands are in `docs/shots/README.md`, the hero (3D at 3 px per line about page 481) is the README's second image.

Not done, and where it would go: the accented letters (a cp1252 atlas), a chapter band within the page grid (needs a non-rectangular directory), and hyphenated reflow instead of Gutenberg's breaks (a layout that knows the page width in glyphs, which is the proportional-face work).
